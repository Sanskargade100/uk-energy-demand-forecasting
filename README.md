# UK Energy Demand Forecasting

Forecasting Great Britain's electricity demand for every 30-minute settlement period
over the next **48 hours**, with calibrated **80%** and **95%** prediction intervals.

> **Headline results** (test year 2025, evaluated at daily origins):
>
> - **Best model:** XGBoost
> - **Test MAE:** 1,140 MW (WAPE 4.36%)
> - **Improvement over weekly-baseline MAE:** ~48% (2,185 → 1,140 MW)
> - **95% interval coverage:** 89.7% (nominal 95%; conformal, calibrated on 2024 — see note)
> - **Forecast horizon:** 48 hours (96 half-hourly steps)

## Project overview

An end-to-end, tested forecasting system: it ingests official half-hourly demand,
weather and holiday data; cleans and validates it (including UK daylight-saving
edge cases); engineers leakage-safe features; compares statistical, machine-learning
and deep-learning models under **walk-forward** validation; and produces calibrated
prediction intervals. Reusable logic lives in `src/energy_forecasting/`; notebooks
are for investigation only.

## Business problem

System operators and traders must anticipate demand to balance the grid and buy
energy economically. Errors are costly in both directions, so a good forecast needs
not just an accurate point estimate but an honest sense of its own uncertainty —
hence the prediction intervals and the emphasis on **operational** metrics (MAE,
WAPE, interval reliability) over R² alone.

## Data sources

| Source | What | Access |
|--------|------|--------|
| **NESO Historic Demand Data** | Half-hourly GB National Demand (ND, MW), 2020–2025 | NESO Open Data Licence (fetched at build time, not vendored) |
| **Open-Meteo** | Hourly weather for 6 GB cities (archive + historical-forecast APIs) | No key required |
| **GOV.UK Bank Holidays** | England-&-Wales / Scotland / NI calendars | Public API |

## Methodology

- **Target:** NESO National Demand (ND) in MW at 30-minute resolution; horizon 96 periods.
- **Timestamps:** built DST-correctly — clock-change days have 46 or 50 periods, never assumed 48.
- **Leakage control:** rolling/lag features use only past demand; weather at future
  timestamps comes from a *forecast*; the final test year is untouched until selection is done.
- **Validation:** chronological split (train 2020–2023, validate 2024, test 2025) plus
  expanding-window backtesting for model selection.

## Feature engineering

Calendar (hour, settlement slot, day/week/month, cyclical sin/cos, days-to/from Christmas),
holiday flags (GB population-weighted), demand lags (1, 2, 48, 96, 336) and rolling
statistics (mean/std/min/max, computed on `shift(1)` to prevent target leakage), and
temperature features (heating/cooling degrees, squared, lag, rolling mean).

## Backtesting design

Never a random split. Expanding-window folds: train on everything up to a month
boundary, validate the next month, then grow the window. The 48-hour forecast is
issued from daily origins across the validation/test window. See
`src/energy_forecasting/evaluation/backtesting.py`.

## Models

| Model | Role | Multi-step strategy |
|-------|------|---------------------|
| Seasonal-naive (last value / yesterday / last week / 4-week avg) | Baselines to beat | seasonal lookback |
| SARIMAX (+ Fourier weekly/annual, exog temp/holiday/weekend) | Statistical benchmark | direct |
| **XGBoost** | Primary ML model | horizon-feature |
| LSTM (336 → 96) | Deep-learning comparison | sequence-to-sequence |

Deep learning is **not assumed** to beat XGBoost; results are reported honestly.

## Results

Generated by `scripts/evaluate_models.py` → `reports/model_comparison.csv`.

| Model | MAE (MW) | RMSE (MW) | WAPE (%) | Peak MAE (MW) | Training time |
|-------|----------|-----------|----------|---------------|---------------|
| **XGBoost** | **1,140** | **1,527** | **4.36** | **1,109** | ~2.5 min |
| Baseline: 4-week average | 2,080 | 2,802 | 7.95 | 3,163 | — |
| Baseline: last week | 2,185 | 2,921 | 8.35 | 3,161 | — |
| Baseline: yesterday | 2,209 | 3,020 | 8.44 | 2,318 | — |
| Baseline: last value | 4,644 | 6,106 | 17.75 | 12,301 | — |

XGBoost roughly **halves** the error of the best seasonal baseline, and notably
improves peak-demand accuracy (Peak MAE 1,109 vs ~3,160 for the seasonal baselines).
SARIMAX and the LSTM are optional secondary benchmarks (run with `--with-sarimax` /
`pytest -m slow`). Selection is on MAE / WAPE / reliability / speed — not R² alone.

## Prediction intervals

Model-independent **conformal** intervals, calibrated per horizon group (1–12,
13–48, 49–96) on validation residuals. Coverage and width are **tested** on the
untouched test year (`reports/interval_coverage.csv`):

| Nominal | Empirical coverage | Avg width (MW) |
|---------|--------------------|----------------|
| 80% | 68.2% | 2,611 |
| 95% | 89.7% | 4,835 |

The bands **under-cover** on 2025. This is reported honestly rather than hidden: the
likely cause is that the 2024 residuals used for calibration were also seen during
early stopping, so they understate true error on an unseen year. A cleaner
calibration split (a slice not used for early stopping) would widen the bands toward
nominal — a documented next step.

## Installation

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"          # add ".[deep]" for TensorFlow (LSTM)
cp .env.example .env
```

## Running the pipeline

```bash
python scripts/download_data.py --source all              # NESO demand + weather + holidays
python scripts/prepare_data.py --to-sql                   # validate → clean → processed table → SQLite
python -m energy_forecasting.features.build_features      # feature matrix
python scripts/train_models.py                            # train XGBoost + calibrate intervals
python scripts/evaluate_models.py                         # test-year comparison → reports/
```

## Running tests

```bash
pytest              # fast suite (skips slow deep-learning training)
pytest -m slow      # include the LSTM training test
ruff check .
```

## Limitations

- SARIMAX and LSTM are secondary benchmarks; the production path is XGBoost.
- NESO notes known data-quality issues in the historic demand set; the validator
  reports gaps/anomalies rather than hiding them.
- Weather features assume a forecast is available at prediction time; use the
  Open-Meteo *historical-forecast* source (not the reanalysis archive) for a
  leakage-free operational backtest.
